== Overview

The OGC API - Joins core module specifies three operation sets: __discovery operations__, __data joining operations__ and __direct joining operations__. <<core-overview-table,Table 3>> contains an overview of the operations specified in the core module. The implementation of __discovery operations__ is mandatory together with the implementations of either __data joining operations__ and/or __direct joining operations__ operation set.

=== Discovery operations

__Discovery operations__ defines operations for accessing the API landing page, the API definition document, and the information on the server implementation's conformance to the Joins API Standard. The implementation of the __discovery operations__ is mandatory and it is defined in the <<rc_core,requirements class "Core">>.

The `Landing page` (path `/`) provides an entry point to the API. It contains links to:

* The `API definition` (link relations `service-desc` and `service-doc`).
* The `Conformance declaration` (path `/conformance`, link relation `http://www.opengis.net/def/rel/ogc/1.0/conformance`).
* The `Collections` (path `/collections`, link relation `http://www.opengis.net/def/rel/ogc/1.0/data`).

The `API definition` describes the capabilities of the server that can be used by clients to connect to the server or by development tools to support the implementation of servers and clients. Accessing the `API definition` using HTTP GET returns a description of the deployed API implementation instance. The API definition can be hosted on the API server(s) or on a separate server.

The `Conformance declaration` states the conformance classes from standards or community specifications, identified by a URI, that the API implementation instance conforms to. Clients can - but are not required to use this information. Accessing the `Conformance declaration` using HTTP GET returns the list of URIs of conformance classes implemented by the server.
The conformance class values defined in this document are listed in <<conformance_classes_table, Table 1>>.


=== Data Joining Operations

__Data joining operations__ defines operations for accessing metadata and key fields on the feature collections that are available on the server, operations for creating a join source related to some collection that saves data on the server, operations for accessing and deleting the created join sources and `/items` operation that can be used for joining data from the join source with the collection's features. The __data joining operations__ is defined in the requirements classes <<rc_data_joining,"Data Joining">> and <<rc_join_source_delete,"Join Source Delete">>. For this operation set, the implementation of the "Data Joining" requirements class is mandatory and the implementation of the "Join Source Delete" requirements class is optional.

The __data joining operations__ contains following functionalities:

* Accessing the `Collections` using HTTP GET returns a list of feature collections that are available on the server. 

* Each `Collection` element in the Collections list can be accessed further in order to get the metadata on each individual Collection by making an HTTP GET request at path `/collections/{collectionId}`.

* Accessing the `Collection's Key Fields` using HTTP GET at path `/collections/{collectionId}/keys` provides information on the key fields of a Collection.

* Accessing the `Join Sources` using HTTP GET at path `/collections/{collectionId}/joins`returns a list of join sources that are related to a specific collection that are available on the server. 

* New `Join Sources` can be created by making a HTTP POST query at path `/collections/{collectionId}/joins`. This standard contains support for CSV input data format. The input data can be either uploaded to the server, represented by the requirements class "<<rc_file_uploading_with_query, Input File Upload>>" or they can be referenced via URL links, represented by the requirements class "<<rc_file_referencing_with_url, File Referencing with URL>>". 

* The metadata of each `Join Source` resource can be accessed by making an HTTP GET request at path `/collections/{collectionId}/joins/{joinId}`.

* Each `Join Source` can be deleted by making a HTTP DELETE request at path `/collections/{collectionId}/joins/{joinId}`.

* The join source data can be joined with the collection's features at path `/collections/{collectionId}/items` by providing in the query a reference to a join source with the `joinId` parameter.


=== Direct Joining Operations

__Direct joining operations__ defines functionality for joining data from an input data source directly with an other input data source.

* The data from the input data source can be joined directly with other input data source by making a HTTP POST request at path `/direct-join`. This standard contains support for joining data from CSV files to GeoJSON files. The result of the direct-join operation is the GeoJSON document that contains also the joined attributes from the CSV file. The input data can be either uploaded to the server, represented by the requirements class "<<rc_file_uploading_with_query, Input File Upload>>" or they can be referenced via URL links, represented by the requirements class <<rc_file_referencing_with_url, File Referencing with URL>>". 


=== Encodings

The use of a "<<rc_json, JSON>>" encoding is mandatory for service responses in operation sets __discovery operations__ and __data joining operations__. In addition, support for "<<rc_html, HTML>>" encoding is recommended.

Support for the "<<rc_geojson, GeoJSON>>" encoding for the joined data is mandatory for  __data joining operations__ and __direct joining operations__.
